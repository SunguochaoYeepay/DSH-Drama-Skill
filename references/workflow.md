# 流程与人工闸门

进入新项目、恢复中断项目或准备推进阶段时读取本文件。

**开始生成之前**先看 [`preflight.md`](preflight.md)：它管环境体检、付费预算和提示词自检，本文件管流程与闸门。

## 立项入口

剧本阶段**默认走 Agent 直写**：`cli/script.mjs register-agent --input <草稿> --out <项目/story.md>` —— 草稿由**当前对话的 Agent 自己写**，用户不满意改完重新登记即可，不绕付费模型，票据记 `agent_draft` 与 `drafted_by`。**"剧本必须用外部大模型写"这条旧约束已作废**：写剧本要的理解和判断当前对话模型就有，再调一次 `qwen3.8-max` 只是多绕一圈、多一个改一个字就要重跑的锁定成本。另两条来源：`cli/script.mjs generate --input <素材> --out <项目/story.md>` 走 `.env` 的 `AIH_SCRIPT_MODEL` 模型生成 —— **可选，只有用户明确要求"用模型写一版"时才用**；用户原稿仅经其明确确认后用 `register-user --input <原稿> --out <项目/story.md> --confirmed-by <确认者>` 登记。三者都留来源票，记录输入与剧本哈希。`generate` 与导演共用直连流式 Responses：只接受服务起始和完成事件中的相同模型、完整响应与非空正文；默认推理强度 `low`。文本请求超时及两阶段输出上限从根目录 `.env` 读取（见 `.env.example`）。来源票 `story.provenance.json` 记录输入与剧本哈希、请求及响应模型。不得代签、不得把历史未知来源补写成模型创作、不得把 Agent 直写稿标成模型产物。逐字阅读剧本后，用 `cli/review-gate.mjs approve --project <项目> --stage story` 记录人工票。旧 `src/board.mjs story/from-story` 已停用。

**改剧本是一次全链路改动，不是改一个文件。** 用户明确授权修改剧本后，按顺序做四件事，漏一件就会出错：

1. **备份并删掉 `story.md` 与 `story.provenance.json`** —— `register-agent` 拒绝覆盖已存在的剧本（"先人工审阅现有项目，不能静默覆盖"）。老剧本的备份留进项目 `.tmp`。
2. **重新登记、重新人工确认** —— 剧本原文一变，`story` 票自动失效。
3. **用 `init-board` 重建板子，不是"同步"** —— `board.json` 的索引镜头与**台词文本**都是从剧本编译出来的；只同步 Brief 的字段会让板子留着旧行号与旧台词，而下游的台词正是靠板子里那份文本搬运的。重建会清空已生成的资源槽位，所以先备份旧板子，重建后把 `characters[].portrait` / `identities[].sheet` / `scenes[].master` 三类槽位照抄回来（`pot_hit` 2026-09-20 实测：9 个槽位全部无损搬回）。
4. **重算导演稿里的 `lines` 行号** —— 行号是剧本的**行序号**，插一句、删一句都会让后面整体移位。`pot_hit` 实测：加入小猫之后两句台词从 L15/L18 变成 **L18/L21**；照抄旧行号会让台词搬到**动作行**上去。

另外：`cli/keyframes.mjs` 会读项目里的 `asset-design.json`（上一次 `design-assets` 的产物），**它不会跟着板子自动更新** —— 重建板子之后必须重跑 `cli/design-assets.mjs`，否则提示词里会混进过期的造型文本（详见 [`assets-and-keyframes.md`](assets-and-keyframes.md)）。

按 [`board-brief.example.json`](board-brief.example.json) 准备已确认的剧名、项目 id、风格、画幅、人物设定及故事概述，再运行 `node cli/init-board.mjs --story <项目/story.md> --brief <项目/board-brief.json> --out <项目/board.json>`。此入口只做结构化解析和台词搬运，不代写 Brief、不代签人工票；索引镜头不替代导演方案。

**板子建完要人工确认**：`node cli/review-gate.mjs approve --project <项目> --stage board`。场景清单、角色、造型、道具都住在 `board.json` 里，而它**此前全程无票**（`no_chute` 2026-09-20：按"机位里外"二分场景，漏掉了"舱门口/跳板"这个真正的叙事空间，一路绿灯到 g001 出图才发现——画面是一架门关着的飞机）。确认要点就一条：**剧本里每个需要人物处在某个位置的动作，那个位置在场景清单里有没有名字、有没有主图。** 改板子会让这张票失效，资源与关键帧入口都会拦。

导演方案确认后**可选**运行 `node cli/design-assets.mjs <项目/board.json> --out <项目/asset-design.json>`。场景师只编译空间和光线，人物造型师只编译脸、妆发、服装和连续性；两者不能改剧情或镜头。

**这一步是参谋，不是闸门。** 资源阶段读 `board.json`，不读 `asset-design.json`；关键帧只消费其中的人物造型条目（`compileCharacterDesign`），场景设计一条都不进提示词。`asset-design.json` 里 `status: 'director_review_pending'` 只写不读，没有入口检查它 —— 所以它**不需要导演审核，也不需要人工票**，跳过不会阻断后续任何步骤；资源阶段的人工资源票才是这道关。

想改资源阶段的出图，改的是 `board.json`（`scene.environment`、`character.face_prompt`、`identity.appearance_details`）；想改全片镜头与光，改的是 `cinematography.json`。改设计方案对这两处都没有效果。

导演稿有**两条合法来源，默认走第 2 条**，两条都必须按 [`director/brief.md`](director/brief.md) + [`director/schema.md`](director/schema.md) 的契约交付：

1. **对话里的 Agent 直写（默认）** —— 与剧本 `register-agent` 对称：**分镜分析要的判断力当前对话模型就有**，不需要再调一次外部大模型。草稿按契约写出后用 `cli/register-direction.mjs <board.json> --input <草稿.json>` 登记；票据记 `provider: agent_draft` / `model: null` / `authored_by`，**不得冒充模型产物**。
2. **`cli/direct.mjs <board.json>`** 调 `AIH_DIRECTOR_MODEL` 指定的模型 —— **可选，默认不走**（只有用户明确要求"用模型出一版"时才用；不限制厂商或型号）。非分批路径直读流式 Responses 的起始与完成事件；默认推理强度 `low`，显式 `--thinking` 才用 `xhigh`（模型默认 `xhigh` 会占用大量输出 token）。必须确认完整结束、两个事件都报告与请求相同的模型、且正文可解析，才写 `board.direction.json.provenance.json`。`--batched` 改走 chat/completions 的结构化输出，先规划单元再逐单元设计。`bl --stream` 的 content-only 摘要不报告模型，不得据此生成来源票。

**判据不是「必须由另一个模型写」，而是「必须按契约交付，且单元边界诚实」。** `AIH_DIRECTOR_MODEL` 的白名单和机器校验都已取消，唯一把关的是人工审阅；两条来源的票据都绑定板子、剧本和导演稿，**只作留痕，不再作为放行前提**。统一配置见根目录 `.env`（可参照 `.env.example`），敏感凭据可放本地 `.env` 或已有 CLI 凭据存储。

收到短句、故事点子或没有制作规格的剧本时，第一步不是扩写，而是补齐项目 Brief。

必填且必须由用户明确提供或确认：

- `style` / `style_prompt`：视觉媒介和整体美术方向。
- `aspect`：目标画幅，如 `9:16`、`16:9`、`1:1`。
- `input_references`：已有核心人物、场景或道具图片及其职责；没有则记录为空。

不得沿用上一部剧的风格或画幅，不得静默使用默认值。用户已经在请求中给出时直接记录，不重复追问。

### 已有人物图片

用户在入口提供核心人物图片时：

1. 先确认图片对应的角色。
2. 确认它是身份硬参考还是风格/灵感参考。
3. 确认锁定范围：脸或头部、体型、服装、发型配饰、整体风格。
4. 将原图复制到项目的 `inputs/references/`，保持原文件不变，并在契约中记录来源和职责。
5. 检查分辨率、清晰度、遮挡、视角和烧字；检查结果交给用户看。

核心人物原图若被指定为身份硬参考，后续不能重新设计该角色。资源阶段只补齐模型所需但原图缺失的肖像、全身身份图或其他视角，并让用户确认派生资产是否仍是同一个角色。

参考图片自身的宽高比不等于成片画幅，不能从一张竖图自动推断项目必须做 `9:16`；画幅仍需单独确认。

按需确认而非固定盘问：

- 目标平台或发布场景。
- 期望总时长或集数。
- 对白语言、受众和内容边界。
- 测试片还是正式交付。

只有这些信息会显著改变当前故事结构、构图或生成成本，并且无法从上下文判断时才询问。

## 导演分批模式

`cli/direct.mjs <board.json> --batched` 先按剧情规划生成单元，再逐单元设计镜头，最后由代码合并成一份正式导演稿。单元数量由剧本决定，不得预设或为调用次数人为切分；任一单元失败都不写正式导演稿。合并后不再跑机器校验，能否进入下一阶段由人工审阅决定。

## 状态机

| 阶段产物 | 人工审阅物 | 下一步条件 |
|---|---|---|
| 项目 Brief | 风格、比例、参考图及必要交付要求 | 用户确认立项参数 |
| 剧本 | 完整剧本；行号、角色、场景和台词结构由人自己核对 | 用户确认剧本 |
| 导演方案 | 时间轴与单元表；时长、台词覆盖和动作复杂度由人自己核对 | 用户确认导演方案 |
| 资源 | 角色/场景/道具总览和原图 | 用户确认资源 |
| 关键帧 | 编号总览和逐张原图 | 用户确认整组关键帧 |
| 单段视频 | 完整视频、首尾帧、八帧总览 | 用户确认该段 |
| 成片 | 完整成片和接缝总览 | 用户最终确认 |

没有机器检查这一环：产物生成后直接送审。用户没有明确通过，就不进入下一阶段。

## 串行规则

- 导演方案未确认，不编译正式生成计划。
- 资源未确认，不生成关键帧。
- 关键帧未整组确认，不生成第一段视频。
- `g001` 未确认，不生成 `g002`；依次类推。
- 后一单元若需要参考前段实际姿态、身份或空间状态，先提取并人工确认前段稳定尾帧，再生成后一关键帧；不能只靠导演文字猜接缝。即使剧情在这里切开、动作不连续，也必须把该单元标成 `reference_previous`；只有完全不需要上一段产物时才可用 `independent`。
- 计划中任一视频段未确认，不允许合成。
- 成片合成后仍需人工终审。

视频串行不仅是资源限制，也是质量反馈机制：前一段暴露的人物漂移、动作失控或对白截断，应在下一段生成前修正规则。

## 票据

新版票据位于项目目录的 `review.approvals.json`：

- `direction`：导演方案确认。
- `story`：剧本原文确认；与模型/用户来源票是两件不同的事。
- `assets`：角色肖像、造型身份图、场景主图和道具参考图整组确认。
- `keyframes`：完整关键帧集合确认。
- `clips.<unit-id>`：每段视频独立确认。
- `handoffs.<unit-id>`：连续承接单元的实际稳定尾帧确认。
- `final`：最终成片确认。

票据包含审阅人、时间和产物哈希。哈希与当前文件不一致时票据失效，不能手动沿用。

旧 storyboard 的 `meta.approvals.story/shots/assets/keyframes` 暂时保留兼容，但新版导演和逐段视频流程以 `review.approvals.json` 为准。

## 审阅交互

送审时必须把实际产物呈现给用户，而不是只给路径或报告：

- **剧本**：**不能只给剧本原文**。原文看不出因果缺口和物理错误（文字甚至可能是对的），所以要同时给一段**白话预演** —— 按**剧本的场面/段落**（不是导演稿的 shot，此刻导演稿还不存在）讲清楚：这一段画面上会看到什么、观众此刻知道什么、角色此刻知道什么。预演同时要回答 `SKILL.md` 里的故事三问（意外凭什么发生／谁先知情／物理是否自洽）—— **三问的答案就是这段预演本身**。`pot_hit`（2026-09-20）实测：只给文本时，「花盆没有掉落的原因」和「花盆从她身后飞上来」这两个洞在故事闸门上完全看不见，直到成片才被用户发现。
- 图片：总览图加可打开的原图。
- 视频：完整视频加多帧总览；需要判断衔接时再加首尾帧。
- 音频：播放或提供完整视频实听，不能仅凭响度数字判断台词是否正常。
- 导演方案：展示单元时长、切分原因、高风险动作和台词归属。

用户指出问题时，只重跑受影响阶段及其下游。上游产物未变化且票据仍有效时，不要求重复确认。

## 局部返修分支

后续阶段发现单个镜头的姿态、走位、构图或动作不可执行时，走局部返修，不推翻已确认剧本。剧本票继续有效；导演只针对受影响的生成单元补充或修订空间调度、`keyframe_start`、`end_state`、镜头动作和必要的连续性交接，不能把技术返修意见写回 `story.md`。

返修顺序固定为：

1. 先记录问题和受影响单元，例如“g001 人物没有沿床长边躺下”；判断是导演空间调度缺失、执行提示词编译缺陷，还是生成抽卡波动。
2. 如果问题只是执行层约束缺失、提示词没有把已有动作翻译成可执行几何关系，当前 Agent 直接修改该单元的直写提示词（`keyframe-prompts/<unit-id>.txt`，2026-09-21 起关键帧提示词的唯一来源）并重跑；不需要外部模型，也不改导演语义。这个能力适用于所有剧目，不是某个故事的特例。
3. 若问题改变了空间调度、动作定义、单元边界或连续性决策，使用 `node cli/revise-unit.mjs <board.json> --unit <id> --feedback <revision.md>` 召回导演做**单元级修订**；场景师只修环境，人物造型师只修身份/服装，不能替导演决定人物怎么运动。
4. 只有导演稿被修改时，才重新运行导演校验并生成新的导演来源票据；导演方案人工票据因导演稿哈希变化自动失效，必须重新确认修订单元或修订方案。
5. 修改直写提示词不改变导演稿，但仍必须重新生成并人工确认受影响的关键帧/视频；计划不变时不要求重签剧本或导演票。
6. 重新编译 `render.plan.json`。导演稿变化时旧计划不能继续执行；剧本来源票不需要重签，资源票只有在引用的资源文件变化时才需要重签。
7. 从修订单元开始，按依赖链重跑关键帧、视频并逐段人工确认。与该单元没有依赖关系的已确认产物保留。
8. 若后续单元是 `continue_previous`，修订单元的视频和稳定尾帧变化会使后续交接票失效；从第一个受影响的承接单元重新提取尾帧、确认 handoff，再继续生成。

影响范围：

| 发现的问题 | 需要重做 | 不需要重做 |
|---|---|---|
| 关键帧空间姿态不对 | 该单元关键帧、该单元视频及其承接链 | 剧本、无依赖的资源和单元 |
| 视频动作失控但关键帧正确 | 该单元视频 | 关键帧、上游导演和剧本 |
| 角色脸/服装身份不一致 | 受影响资源、引用它的关键帧和视频 | 不引用该资源的单元 |
| 故事、台词或人物设定真的改变 | 从剧本开始重新走票据链 | 不保留旧剧本票 |

局部返修必须在项目 `reviews/` 留下问题、原因、修订单元、重跑范围和人工确认结果；不能用“全量重跑”掩盖依赖关系，也不能用旧票据跳过受影响阶段。

## 视频规格与重抽

**视频生成是抽卡：同一条提示词重复生成，结果不同。重复生成是常态，不是异常，也不是流程失败。**
工作流必须按这个前提组织 —— **用低分辨率把抽卡成本摊薄**，而不是指望一次通过。

每段视频生成一个当前产物，出片后做技术检查和人工确认。不满意则重抽，重抽后的新产物必须重新确认。

| 选择 | 规格 | 出片后 |
|---|---|---|
| 常规（默认） | FastH3 8 步 + VSA；尺寸由 `.env` 的 `AIH_VIDEO_NORMAL_SIZE` 指定，当前为 `480x864` | 呈现完整视频和多帧总览，等待确认 |
| 高质量（用户明确要求） | `--quality high`；尺寸由 `.env` 的 `AIH_VIDEO_HIGH_SIZE` 指定，当前为 `768x1344` | 同样检查和确认 |

规则：

- 默认 `AIH_VIDEO_QUALITY=normal`；用户说“高质量”时用 `--quality high`。两档都只决定本次生成尺寸，不决定审阅次数。
- 合成也使用同一组 `.env` 尺寸；高质量成片运行 `node cli/assemble-units.mjs <项目/render.plan.json> --quality high`，避免输出被缩回常规尺寸。
- 不满意就按用户意见重抽；默认维持当前规格，明确要求高质量才切换。每段只有一张当前产物的确认票。
- 重抽前先分清原因：**提示词缺陷**（改词修得掉）还是**抽卡波动**（直接重抽）。
  两者都要留存记录，不要靠反复重跑掩盖提示词缺陷。
- 资产和关键帧没有快慢档之分，但同样要抽卡、同样要重复生成：按「重抽 → 重新送审 → 重新确认」处理，
  不能拿旧确认沿用新产物。

## 恢复已有项目

1. 找到 `board.json`、导演方案、生成计划和 `review.approvals.json`。
2. 校验票据对应文件哈希；不要根据文件名猜测是否确认。
3. 找到第一个未确认或已失效的阶段。
4. 展示该阶段现有审阅物，让用户决定通过还是重跑。
5. 从该点继续，不自动重做已确认阶段。

## 停止条件

- 用户要求停止时，等待当前不可安全中断的本地任务结束，然后停止后续任务。
- 生成失败或人工拒绝时，不推进下一阶段。
- 涉及付费重跑时，先说明重跑范围和原因；不要无限自动重试。

## 收工与知识回流（`final` 票之后必须执行）

**触发条件：`final` 票据已记录。** 此时项目结束，最后一步不是"交付"，是**把这一轮学到的东西并回知识库**。

不执行这一步，同一个坑会在下一部剧原样重犯 —— 工程里已经有过这样的记录（同一类提示词缺陷被独立发现两次）。

### 零、硬边界：沉淀不等于改文件（2026-09-21 用户拍板）

知识回流的**默认产物是文字**：这一轮踩了什么坑、为什么、下次怎么躲。这层照写，不需要任何人同意。

但**经验永远不能自己变成改动**。以下三类，未经用户逐条点头，**一个字都不许动**：

| 禁区 | 范围 |
|---|---|
| 工程代码 | `src/` `cli/` `tests/` `schema/` `skills/` `plugins/` |
| 规则正本 | `references/` 下所有 `.md`（含 `prompts/`、`director/`、`story-craft/`） |
| 提示词 | 项目侧 `<项目>/keyframe-prompts/*.txt`，以及任何会被逐字送进模型的文件 |

理由：前两类是下一部剧的行为依据，第三类是已送模型的产物。改它们等于替用户改决策 —— 而"确认了 A 交付了 B"正是这套闸门要防的事。

> 已生成的 `keyframe-prompts/<unit-id>.txt` **永不回溯改写**，即使后来发现更好的写法。要变就重跑那一单元，重跑本身要过闸门。
>
> 同理，`references/` 里的规则一改，下一部剧我写出来的提示词就不一样了 —— 这正是"改提示词"的间接形式，所以规则改动同样要过这道闸。

### 一、先分层，别混在一起

| 内容 | 去处 | 写入方式 |
|---|---|---|
| **可复现、会改变后续决策的规则** | 候选提案 → 用户同意后 `references/`（按所有者分文件） | **默认不写**。先提案，同意后才落盘，且与现有内容**去重合并**，不是追加 |
| 本次项目的耗时、文件名、逐帧评价、一次性实验 | 该剧目的 `reviews/` | 追加，不进仓库 |
| 跨会话的流水记录与复盘叙事 | `.workbuddy/memory/<日期>.md` | 按日期追加 |

只有第一类最终可能进 `references/`。**单次项目的具体数字不进规则文件** —— 见 `references/troubleshooting.md` 的「升级为规则的标准」。

### 一·五、改东西之前，先交提案

一条经验若满足可复现、会改变后续决策，**不直接写进 `references/`**，而是列成提案交给用户。每条提案必须有四件事：

1. **目标**：哪个文件的哪一小节（先查有没有所有者；整个领域都没有才新建，并登记进 `SKILL.md` 的「契约所有权」表）。
2. **改前原文**：贴出原句。
3. **改后文字**：贴出新句。
4. **依据**：这一轮的哪个具体事件 + 是否复发（复发加 `🔁 已复发 N 次` 标注）。

补充规则：

- 同一条规则已在别处存在 → 提案是「删掉重复的那份」，不是再加一份。
- **用户未答复 = 不改；用户否决 = 不改，且同一轮不再提交同一条。**
- 涉及人设、剧情、画幅、风格、花钱的，除了提案还要单独停下来问。
- 能改成代码/校验器拦住的，在提案里写明"建议改代码"与理由，代码改动同样等同意，且必须带测试。

### 一·六、临时脚本：落点、转正、清理（2026-09-21 用户拍板）

排查问题时现写的脚本是**脚手架，不是交付物**。它们有固定去处，且会话结束前要处置掉。

| 情形 | 处置 |
|---|---|
| 一次性诊断（查完就扔） | 落在 `.tmp/`（**根目录零容忍**），用完即删 |
| 同一件事写过两次以上 | 说明工程缺这个入口 → **提案转正成 `cli/` 工具**，带行为测试 |
| 已经被别处引用（记忆/reviews 里按名字提过） | 先确认引用失效，再删；不确定就留着并标注 |

判定"该不该转正"的硬信号：**同一个功能被独立写了 N 遍**（干跑包装器、ffmpeg 探测、跑测试的封装都出现过 3–8 个版本）。
那不是懒，是工程没给入口 —— 转正治根，删掉治标。

> 本节的由来：一次会话在仓库根目录堆了 11 个 `.tmp-*.mjs`，`.tmp/` 里另有 120 项，
> 其中 `step1…step16` 是把整条流水线在外头重抄了一遍、`memory-write` 写了 8 版、`run-tests` 写了 3 个。
> `.gitignore` 的 `.tmp-*` 只挡住了 git，**没挡住堆积**，所以补这一条。

### 二、合并必须去重，不允许堆积

> 以下动作全部发生在**用户同意之后**。同意前不存在"合并"，只有提案。

对每一条候选规则：

1. **先查有没有所有者**：`grep` 全部 `references/*.md`，看这条是否已被写过。
2. 已有 → **改那一条**（补强措辞、补实测证据、补反例），**不要在新位置重写一遍**。
3. 没有 → 找到它所属的领域，写进那个文件的对应小节；若整个领域都没有所有者，才新建文件，并登记到 `SKILL.md` 的「契约所有权」表。
4. **同一规则出现在两个文件里 = 回归缺陷**，按 `SKILL.md` 的所有权表删掉重复的那份，只留所有者。

### 三、复发要标注（这是本机制的重点）

一条规则**再次被违反**时，说明它写在那儿但没拦住人。此时**不能只是再写一遍**，要在规则所有者里给它加醒目标注：

```markdown
> 🔁 **已复发 N 次（最近：<剧目> <日期>）**：<一句话说明这次是怎么犯的>
```

> 用 `🔁` 而不是 `⛔`：`references/director/schema.md` 已经用 `⛔` 表示「你没有资格做的事」，
> 两者语义不同，符号要分开，否则标注会被误读。

约定：

- 标注写在**规则所有者文件里、紧贴该规则**，不要写在 `SKILL.md` —— 入口文件只放路由，不放规则。
- 复发过一次的规则，在**前置清单**（`references/preflight.md`）里升级为**开机前必查项**；只写过、没复发过的规则不必占那个位置。
- 复发时同时做一件事：**判断能不能改成代码或校验器来拦**。能被确定性代码拦住的，就去改代码 + 加负例测试，然后把规则标注降级为"已由代码兜底"。
  本次实例：`keyframe_cast` 与 `keyframe_start` 不一致导致服装漂移 —— 复发过，正确处置是把「首帧描述里提到的人是否都在 `keyframe_cast` 里」写成人工必查项并升级进 `preflight.md`，而不是只把文档写得更长。（2026-09-19：当初给它加的机器校验 `validateDirection` 已随「去掉机器审核」移除，规则本身仍然成立。）

# 计划身份证与历史计划隔离

每份 `render.plan.json` 会记下它是从哪份 `board.json`、`story.md` 和导演稿编译出来的（`plan.provenance`），**只作留痕，不作闸门**。

这意味着跨剧目沿用旧计划、手改 `render.plan.json`、换了剧本或导演稿却没重编 —— 都不会被代码拦住。判断这份计划还对不对，是人的事。想确认来源时看 `plan.provenance` 里的哈希；要重建就重跑 `cli/compile-units.mjs`。

导演协议版本也不再设下限：旧协议导演稿可以直接编译，编译结果是否可用由人判断。

`cli/migrate-plan.mjs` 保留为「给历史计划补一份当前项目身份证」的工具，不再是继续旧项目的必经步骤。

合成时，含台词的 H3 片段保留完整生成时长。导演的最低口播秒数只能用于规划，不能作为后期硬裁点；H3 实际语速可能更慢。无台词片段才允许按导演内容时长裁掉生成网格余量。
