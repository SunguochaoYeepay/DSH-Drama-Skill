# 抽卡师

抽卡师是导演和生图模型之间的执行编译层，并且是**抽卡闭环的主人** —— 它要对"这张关键帧最终对不对"负责到底，不只是把导演的意图翻译一遍。它不创作剧情，也不拥有台词、角色设定、场景语义或单元边界；它把导演已经决定的镜头意图翻译成当前生图模型可执行、可检查的语言，并在出图不合格时负责分诊、迭代、喊停和留档（见「抽卡闭环」一节）。

## 输入与输出

输入包括导演单元、关键帧起始姿态、景别、机位、出镜角色、参考图职责和项目级执行覆盖。输出至少包含：

- 原始意图（不得丢失）。
- 人物身份、场景、姿态和空间几何约束。
- 参考图职责和模型语言。
- 冲突列表；不能满足的约束要报告，不得静默随机妥协。
- 最终生图提示词和必要的执行层补充。

时间轴词必须翻译成静态画面词：例如“0秒时女孩仰面躺着”应变成“关键帧起始姿态：女孩仰面躺着”，不能把视频时间直接喂给生图模型。

抽卡师可以把“躺着”“站在床边”等软动作展开成可验证的几何关系，但不得擅自改变动作。若“近景”无法证明“沿床长边躺下”，必须报告景别冲突，由导演或人工决定是否改成中景；抽卡师不能静默改景别。

抽卡师的结果要随生成记录留痕。

## 输出的硬约束：见 `references/prompt-rules.md`

抽卡师产出的最终提示词**必须**遵守 `references/prompt-rules.md`。摘要：

- **提示词的消费者只有文本编码器** —— 没有规则执行器、没有层级、没有截断（只有稀释）。
- **只允许两类内容**：画面内容，加两条实测有效的约束（身份锚、禁文字）。
- **禁止七类**：元标签 / 组织架构、对模型的策略建议、空引用、解释性文字、正向里的否定句、
  单帧不可见的信息（运动方向、时序「尚未…」）、拼接疤痕。
- **字数 ≤ 500 字**（`PROMPT_MAX_CHARS`，2026-09-20 由 350 放宽；350 仍是纯画面描述的理想值），同一件事只说一次。

⚠ **元标签不只是没用，它有被画出来的风险**：「抽卡师」「导演」「执行层」这类词在中文里能读作
职业/人物，模型可能把它们编进画面。**任何组织架构词都不许出现在送模型的字符串里。**

打印给人看的版本可以带【】标签分段，**送模型的版本不行** —— 两个版本必须分开。

## 抽卡闭环：抽卡师是主人，不是一次性翻译

> **定位（2026-09-20 用户拍板）**：首版提示词来自导演，但「这张关键帧出得对不对」由抽卡师负责到底。
> 补完执行层那一段就撒手、把「不满意」原样丢回给人和导演 —— 那是失职，不是分工。

负责到底意味着拥有四件事，缺一件就不算负责：

| 权 | 内容 | 现在的工程状态 |
|---|---|---|
| 判断 | 这张废在哪：编译冲突 / 提示词缺陷 / 抽卡波动 | 靠人看图，无规程 |
| 迭代 | 下一版改什么（写覆盖、改契约措辞） | 有 `reviews/keyframe-overrides.json` |
| 停止 | 同一张抽到第几张必须停手 | **没有上限** |
| 记录 | 每版留档：抽过什么、为什么废 | **工程不支持，见文末缺口** |

**先分诊，再动手 —— 只有第三类才值得重抽：**

1. **编译冲突** —— 提示词内部自相矛盾（景深给了两个值、排除项禁「过曝」而规则又要「过曝」）。重抽无效，改提示词。
2. **提示词缺陷** —— 该说的没说，或说了模型听不进（否定式、解释性文字挤掉核心指令）。重抽无效，改措辞。
3. **抽卡波动** —— 同一份提示词，模型有时给对有时不给对。**只有这一类才该重抽。**

`no_chute`（2026-09-20）实测：同提示词 v6/v7 两连抽，一张接近、一张全崩。
那不是第 3 类在起作用，是**前两类还没修完就急着摇骰子** —— 判断顺序错了，抽多少次都是白烧 GPU。

**上限纪律**：同一张关键帧**连抽 3 次**仍全废，必须停下来报人，并给出「我认为该改输入」的结论
（改提示词 / 改覆盖 / 改导演稿调度）。不许靠继续抽碰运气 —— 那不是改进，是消耗 GPU 和人的耐心。

**报人时必须请人一起分诊（用户 2026-09-20 补充）**：把抽过的几版图摊开对比，逐版列缺陷与残留冲突，
然后请拍板的人判断 —— **是提示词还没修干净，还是模型扛不动这个镜头**。前者继续改输入，后者该换模型 /
调工作流 / 改调度。抽卡师自己给结论，但拍板在人。

**与导演的边界：抽卡师改输入，不改导演稿。**
覆盖文件与契约措辞是它的工具；首帧调度、姿态、景别属于导演稿，要改必须回头找导演**重签 direction 票**。
抽卡师不能为了让图好看而私下改导演稿 —— 用结果倒推意图，闸门就失效了。

⛔ **工程缺口（规则先立，能力待补）**：`cli/keyframes.mjs` 每次生成直接覆盖 `g001.png`，
抽卡历史不可回溯，所以上表第 4 项「记录」目前只能靠人工逐版备份（`g001_v1.png` …）。
自动版本号与 `reviews/keyframe-draws.json` 尚未实现 —— 在工程补上之前，按人工备份执行，每版烧完立刻改名。

## 非人类卡司：取景与承托必须重新推导

> 🔁 **已复发（最近：bike_stare 2026-09-19）**：同一串「承托物、**床头/床尾**、道具和镜面关系」又原样进了两条关键帧提示词（主体分别是站在草地小径上的女生、和骑车的男生 —— **两者都与床无关**）。
> 机器计数：提示词落盘产物里能查到的**至少 3 次关键帧生成、跨 2 个剧目**（`mimi_bone` 1 次 + `bike_stare` 2 次；结果文件每次重跑会被覆盖，所以这是**下限**）。
> 到 2026-09-19 为止，下面那张表列的四处措辞**一处都还没改** —— 记了却没拦住，这正是「复发」的定义。

执行层现成的取景规则是**按人类、且按床上场景**写的。套到四足动物身上会同时注入多条互相无关甚至冲突的约束。已在 `mimi_bone`（2026-09-19，一条趴在客厅地板上的柴犬）实测到四处：

| 现成措辞（代码位置） | 对四足动物为什么不成立 |
|---|---|
| 「中景：画面下边界严格切在**人物的腰部**（腰带/腰线位置）」（`cli/keyframes.mjs` 的景别规则） | 狗没有腰带/腰线；趴姿的中段不是腰 |
| 「承托物、**床头/床尾**、道具和镜面关系」（`cli/keyframes.mjs` 的空间关系） | 客厅地板上的动物没有床头床尾 |
| 「不应出现**鞋子、拖鞋或站立姿态**；不要把身份图中的鞋履和站立姿势复制到**床上躺卧**镜头」（`src/draw-specialist.mjs` 的当前镜头排除） | 没有鞋子，也不在床上 |
| 「严格保持**此人**的脸、发型和服装」（`cli/keyframes.mjs` 的参考图职责） | 不是人 |

**规则**：`characters[].species ≠ human` 时，抽卡师不得让上述人类专用约束原样进提示词，必须换成物种感知的等价物 —— 承托面、四肢落点、身体轴线朝向、头身相对位置。冲突按本文件既有要求**报告**，不得静默随机妥协。

**注意这一条的性质**：成图可能"看起来还行"，但那是模型自己扛住了矛盾，不是契约成立。`mimi_bone` 的关键帧确实出了可用的图，同时也确实带着这四条矛盾 —— 两者可以同时为真，不能拿"图能用"当作"约束没冲突"。

**已有先例**：`cli/keyframes.mjs` 里已经为「老鼠与猫」写过物种专属的体型比例硬约束，说明工程承认需要按物种处理；缺的是把景别与承托这套**通用**规则也补上物种分支。

> **2026-09-20 修复进展**：表中「承托物、床头/床尾、道具和镜面关系」那句**已在 `cli/keyframes.mjs` 改成通用措辞**；覆盖路径那段硬编码的床戏截取范围也已修掉（覆盖文本本身即画面截取范围，并带一条回归测试：覆盖文本里没有的东西，提示词里不许出现）。**表中另外两处仍未改**：景别规则的「切在人物的腰部」、`src/draw-specialist.mjs` 的「鞋子/拖鞋/站立姿态」排除项。

## 多主体同框时，造型描述没有点名归属

执行层把本单元 `on_screen` 的造型描述**按顺序拼成一段**塞进提示词，**没有写明哪一套属于谁**。
`pot_hit`（2026-09-20）实测：两个老头同框，一个该穿浅灰汗衫、另一个该穿深墨绿外套并戴老花镜；
提示词里两套描述并列出现，模型无从分配，结果**把两个人画成了同一张脸、同一件灰汗衫**。

**处置（这条已经可以用覆盖兜住）**：用项目级覆盖 `reviews/keyframe-overrides.json` **逐人点名**：

```jsonc
{ "units": { "g002": "构图覆盖：中景。画面右侧坐着的是大爷：方圆脸、花白短发、不戴眼镜，穿浅灰色短袖汗衫……；画面左侧坐着的是棋友：瘦长脸、灰白长发、戴细金属框老花镜，穿深墨绿色薄外套……两名老人必须长相不同、穿着不同。" } }
```

实测一次到位，两个老人当场变得可辨。**执行层的编译本身还没有做归属**，所以只要两个以上主体同框、且他们的造型需要区分，就应当写覆盖点名。

### 覆盖是按单元 id 索引的 —— 计划一重构就会套错单元

`readKeyframeOverride()` 用 `units.<unitId>` 取文本，而**单元 id 在计划重构后会被复用**（改剧本、改单元数、重新编译，都可能让 `g002` 从"某个单元"变成"另一个单元"）。
`pot_hit`（2026-09-20）实测：为旧的"两个老头"单元写的 `g002` 覆盖，在计划从 3 单元改成 6 单元后**静默套到了小猫单元上** —— 小猫的提示词里凭空多出「画面右侧坐着的是大爷……」，出图里就跟着多出一个**没有被身份锚定**的大爷。

**规矩：改计划必须同步清理或改写 `reviews/keyframe-overrides.json`。** 旧覆盖留档到 `.tmp`，不要留在 `reviews/` 里过夜 —— 它不会报错，只会悄悄地改掉另一个单元的构图。

### 覆盖顺带能屏蔽非人类污染

`applyCompositionOverride()` 会删掉 `构图要求：` 与 `【生成前最终检查】` 两行，而「切在人物腰部」那类人类专用的景别规则正在其中；空间关系行也已改成通用措辞。
`pot_hit` 的猫单元（`species: cat`）实测：干跑提示词里 `腰部 / 腰带 / 鞋 / 站立姿态 / 承托物 / 床头 / 床尾 / 镜面` **一处都没有出现**。
所以只要一个非人类单元本来就需要压构图，**写覆盖是一举两得** —— 既压住构图，又把物种污染一并挡掉。
